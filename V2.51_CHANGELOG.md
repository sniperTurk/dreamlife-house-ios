# DreamLife House v2.51.0 — build 71

## Fix: three-way save conflict can no longer erase a valid candidate

- Reproduced a data-loss case on v2.50: if primary and backup were valid but **different bytes with the same positive journal sequence**, the mere presence of a pending journal bypassed the primary/backup conflict guard.
- With an **older** pending journal, v2.50 discarded that pending copy during load, before recognizing the conflict. With a **newer** pending journal, v2.50 could rotate over the conflicting backup, then promote the pending journal, permanently losing a valid backup candidate.
- On v2.51, the primary/backup equal-sequence check applies **regardless of whether pending exists** and runs **before** pending replay, cleanup or backup rotation. An ambiguous three-way state becomes read-only; all three raw slots are preserved for parent review and CRC32-checked export.
- An already-running store also detects this conflict before staging a write, even when another session left an older pending journal.
- Valid, byte-identical backups and genuinely older backups continue through the normal journal recovery path; no conflict is falsely raised for these safe cases.
- Added five XCTest source cases, one XCUITest source case with an isolated DEBUG-only three-way fixture, and a 24-assertion executable Linux regression suite.
